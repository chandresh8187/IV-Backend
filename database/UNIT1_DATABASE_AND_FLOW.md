# Unit 1 database and flow review

Reviewed on 16 October 2026. Target database: **`u436685010_iv1_app`**.

`u436685010_iv1_app_clean_install.sql` is a fresh-install schema generated by running the current `scripts/migrateUnit1Coils.js` against an empty, isolated database. It contains 17 tables, 10 system-default rows and one requested bootstrap superadmin. It includes the return/reinsert coil workflow. The bootstrap account is `dev@iv.com` with password `12345678`, stored as a bcrypt hash. It contains no copied users, device tokens, machines, inward records, job cards, or production records. No existing database configuration was changed.

## Application and backend flow

The mobile navigation exposes Home, Production, Settings and Profile. Production contains coil inventory, numbered-coil usage, job cards, live production, machine entries and production history. The web uses the same Unit 1 API and database. Older unmounted mobile screens do not require additional database tables.

| Flow | Backend behavior | Tables |
| --- | --- | --- |
| Login and profile | Bcrypt password verification; active-account check; JWT with issuer `iv-api`, audience `iv-unit1`, scope `unit1`; account state rechecked on authenticated requests | `users` |
| Access management | Six roles; default permissions defined in backend code; per-user allow/deny overrides; optional supervisor shift and labour machine assignment | `users`, `user_permission_overrides` |
| Setup | Machines, material grades, material densities, role-specific QR fields, contiguous Day/Night shift boundaries | `unit1_machines`, `unit1_material_grades`, `unit1_material_densities`, `unit1_qr_scan_role_fields`, `unit1_shift_settings` |
| Coil inward | Invoice metadata, one or multiple size lines, physical coil count and batch net weight; each size line is a separate batch | `coils` |
| QR labels and scanning | QR generation timestamp; stable batch reference plus physical coil number; visible fields filtered by role; compatibility and availability checked before insertion | `coils`, `unit1_qr_scan_role_fields`, `unit1_production_runs` |
| Job planning | Customer/project, product, member, section, target pieces, cut length, planned machine, matching material and ordered punch/hole positions | `unit1_job_cards`, `unit1_job_card_holes` |
| Job assignment | An open job is assigned to its planned active machine; competing open assignments/active runs are rejected | `unit1_job_cards`, `unit1_machines`, `unit1_production_runs` |
| Coil insertion | Assigned job, matching material/width/thickness, numbered-coil availability and remaining balance checked transactionally; new run begins in `setup` | `unit1_production_runs`, `unit1_production_events` |
| First-piece approval | All hole dimensions recorded and approved; run becomes `running` | `unit1_run_hole_checks`, `unit1_hole_checks`, `unit1_hole_check_measurements`, `unit1_production_events` |
| Bundle entry | Only approved running runs accept output; records pieces, density, calculated strip usage, punched scrap, member, operator, latest check, shift and operating date | `unit1_production_bundles`, `unit1_production_runs`, `unit1_job_cards`, `unit1_production_events` |
| Pause/resume | Running-time accumulation stops/restarts; paused coil remains assigned | `unit1_production_runs`, `unit1_production_events` |
| Return/change coil | Running or paused coil closes as `returned`; entries remain; remaining stock can be rescanned with the same QR; reinsertion starts a new `setup` run | `unit1_production_runs`, `unit1_production_events`, `unit1_production_bundles` |
| Completion | Run becomes permanently `completed`; job completes when cumulative pieces reach target; batch becomes consumed when all distinct numbered coils are completed | `unit1_production_runs`, `unit1_job_cards`, `coils`, `unit1_production_events` |
| Usage/history | Coil usage sums all runs of each physical coil; job progress sums its runs; production history groups bundle entries by stored operating date/shift, machine, customer, job and material | Existing production tables; no duplicate reporting tables |
| Notifications | Per-installation FCM token registration/removal and test delivery; Firebase service credentials are configured outside SQL | `unit1_fcm_tokens` |
| Realtime updates | Socket.IO resource events invalidate client queries; live production has polling fallback | No additional tables |

Products are defined in backend code: W beam crash barrier, Solar mounting structure, GL Hat Purlin and Purlin C Lip. They do not need a product seed table.

## State and balance rules

```text
Job: open -> completed when total recorded pieces reach the target

Run: setup -> first-piece approval -> running <-> paused
                                      |           |
                                      +-- returned+ -> same coil may start a NEW setup run
                                      +-- completed -> physical coil cannot be reused

Unapproved setup: unassign -> setup run removed; no production entries exist
```

The generated `active_coil_number` column and unique `(coil_id, active_coil_number)` index prevent simultaneous active reuse of a physical coil while permitting multiple historical runs. The permanent unique `(coil_id, coil_number)` index used by older installations is intentionally absent.

Remaining weight is an estimate: original batch weight divided by coil count, minus recorded strip use across every run of that physical coil. Hole scrap is part of strip consumption and is not subtracted twice. There is no scale-measured return balance in the current application. Record all produced bundles before returning a coil.

The schema preserves both first-piece check tables and the newer check history/measurement tables: current routes still write and read both. It also preserves nullable legacy snapshot columns and the application-managed references used by the current migration, rather than adding foreign keys that could change existing edit/delete behavior.

## Import and connect

1. Create or select **`u436685010_iv1_app`** in the hosting database panel/phpMyAdmin. Use an empty database. Import `u436685010_iv1_app_clean_install.sql`. The file has a `USE` statement; its optional `CREATE DATABASE` example is commented out because hosting users often cannot create databases through SQL.
2. Set these backend environment variables with your hosting values:

   ```dotenv
   UNIT1_DB_HOST=YOUR_DATABASE_HOST
   UNIT1_DB_PORT=3306
   UNIT1_DB_USER=YOUR_DATABASE_USER
   UNIT1_DB_PASSWORD=YOUR_DATABASE_PASSWORD
   UNIT1_DB_NAME=u436685010_iv1_app
   ```

3. Keep the general `DB_NAME`/`DB_*` configuration pointing to the existing shared backend/Unit 2 database. `server.js` also runs Unit 2 migrations and background services. Pointing general `DB_NAME` at this Unit 1 database would mix the schemas. This SQL is the Unit 1 database for the current shared server, not a conversion to a standalone Unit 1 server.
4. Configure the backend `JWT_SECRET`. The SQL already creates the requested active superadmin: **dev@iv.com / 12345678**. Its database password field contains a bcrypt hash. No account-creation command is needed for the first login.
5. Restart the backend, sign in, and configure machines, staff and assignments in Settings. For subsequent code/schema updates, run `npm run unit1:migrate` against the configured Unit 1 database. Do not reimport the clean-install SQL over an existing installation.

The SQL deliberately contains plain `CREATE TABLE` statements without table drops or `IF NOT EXISTS`: it is intended for an empty database and should fail visibly on an existing incompatible schema. It requires no stored routines, events, `DEFINER` privileges or disabled foreign-key checks.

## Findings affecting deployment

- Unit 1 mobile debug builds use `http://localhost:5000/api`; release builds automatically use `https://app.ivsquarestructure.com/api`. Unit 1 web development uses the local Vite proxy, while production uses the same live API. See `../docs/UNIT1_UNIT2_HOSTING.md` for hosting configuration.
- The web API uses `VITE_AUTH_API_URL` or `/api`; its Socket.IO connection must also reach the shared backend.
- Unit 1 FCM delivery needs the separate Unit 1 Firebase sender configuration. Its SQL table stores device registrations, not Firebase service-account credentials. The current routes expose registration/status/test delivery; a complete automatic production-alert notification pipeline is not implied by this schema.
- The backend mixes explicit `UTC_TIMESTAMP(3)` writes with session-local `CURRENT_TIMESTAMP(3)` defaults in DATETIME fields. The SQL matches the current backend session timezone (`+05:30`); the bundle shift and operating date are explicit. A timestamp-normalization change would need coordinated backend changes rather than a schema-only timezone switch.
- Two existing Unit 1 tests have expectations that disagree with unchanged runtime behavior: the product-list test expects three products instead of four, and the older permission test expects access that the current permission definitions no longer give. These are separate from SQL import compatibility.

## Verification and reproducibility

Validated on **MariaDB 10.4.32**. The SQL uses MariaDB 10.4+/MySQL 8.0.16+ syntax; a MySQL 8 server was not available for execution testing.

`tests/unit1CleanInstall.integration.test.js` imports the actual SQL file into a newly created isolated database with foreign-key checks enabled. It verifies 17 tables, clean initial data and system seeds, then runs the current migration and compares table definitions to confirm schema parity. It invokes the real backend route handlers for login, material/QR settings, machine creation, coil inward, QR generation/scanning, job creation/assignment, compatibility verification, insertion, first-piece approval, bundles, return, reinsertion, completion, usage and history. This exercises real SQL and business handlers; it does not replace full HTTP authorization, device UI or Firebase delivery testing. The test database is deleted afterward; existing application rows are untouched.

Run from PowerShell in the backend directory:

```powershell
$env:UNIT1_DB_INTEGRATION='1'
node --test tests/unit1CleanInstall.integration.test.js
```

The test requires local database CREATE/DROP privileges and a configured JWT secret. It creates only randomly named `codex_unit1_import_*` databases and removes its own database afterward. It never imports into the named hosting database.

Regenerate the SQL from the current migration with:

```text
node scripts/exportUnit1CleanInstall.js
```

The exporter likewise uses an isolated temporary database and exports system defaults and the explicitly requested bootstrap account. It does not dump the configured application's data.
